1. Layihə haqqında

1.1 Nə edir və niyə belə qurulub

Layihə bir sifariş-ödəniş prosesini modelləşdirir. Sifariş yaradılır, riski qiymətləndirilir, ödəniş gözlənilir — və ya vaxt bitir. Ödəniş gələndə çatdırılma bildirişi göndərilir, invoice yaradılır, proses bitir. Çatdırılma uğursuz olarsa ödəniş geri qaytarılır.

Bu ssenari qəsdən kiçik seçilib: məqsəd çox funksiya deyil, bir dənə real axının üzərində Camunda-nın bütün ciddi mexanizmlərini göstərməkdir. Hər mexanizm süni bir "demo addımı" kimi deyil, həmin axının təbii hissəsi kimi oturur.

Əsas prinsip UI (Thymeleaf) və REST API eyni OrderService-i çağırır. Yəni brauzerdə klikləmək paralel bir kod yolunu deyil, real engine-i işlədir. Demo ilə "əsl" kod arasında fərq yoxdur.

2. Camunda 7 əsasları — bu layihədə

2.1 Embedded engine vs standalone server

Camunda 7-ni işə salmağın iki yolu var və bu, müsahibədə tez-tez qarışdırılır:

YanaşmaNecə işləyirNə vaxt
Embedded
bu layihə		 Engine sizin tətbiqin JVM-ində kitabxana kimi qalxır. RuntimeService, TaskService adi Spring bean-ləridir. Delegate-lər sizin bean-lərinizdir. Engine sizin tranzaksiyanızı paylaşır. Bir tətbiq bir prosesə sahibdir. Mikroservis arxitekturası.
Standalone Ayrıca server (Tomcat/WildFly). Tətbiqlər ona REST ilə müraciət edir. Delegate-lər serverin classpath-ində olmalıdır — ya da external task istifadə edilir. Bir çox komanda bir engine-i paylaşır. Mərkəzi BPM platforması.
build.gradle
// Bu bir sətir engine-i tətbiqin içinə gətirir.
implementation "org.camunda.bpm.springboot:camunda-bpm-spring-boot-starter-webapp:7.24.0"
Diqqət: paylaşılan tranzaksiya Embedded rejimdə orderRepository.save(...) ilə engine-in öz yazıları eyni tranzaksiyadadır. Bu, Bənd 7-dəki outbox pattern-inin işləməsinin səbəbidir — və eyni zamanda delegate-də atılan istisnanın proses addımını da geri qaytarmasının səbəbi.

2.3 Deployment necə baş verir

Spring Boot starter startup-da classpath*:**/*.bpmn, **/*.dmn pattern-i ilə skan edir və tapdığı hər şeyi deploy edir. Fayl dəyişməyibsə yeni versiya yaratmır (checksum müqayisəsi).

Bu avtomatik skan real problem yaratdı Bənd 5-də (migration) v1/v2/v3 modellərini test resource-larına fayl kimi qoysaydım, üçü də context qalxanda deploy olunardı və versiyalaşmanı müşahidə etmək mümkün olmazdı. Ona görə o testdə modellər BPMN Model API ilə kodda qurulur.

4. correlationId və Message Correlation

Problem

Fərz edin ki, eyni anda 10 000 sifariş prosesi işləyir və hər biri öz ödənişini gözləyir. Ödəniş provayderindən webhook gəlir: "filan sifariş ödənildi". Sual: bu bildiriş 10 000 instansiyadan hansına aiddir?

Naiv cavab — process instance id saxlamaq. Amma xarici sistem sizin engine-inizin daxili id-lərini bilmir və bilməməlidir. Bizim tərəfdə isə həmin id yalnız proses başladıqdan sonra yaranır.

Həll: biznes açarı ilə korrelyasiya correlationId — bizim yaratdığımız biznes identifikatorudur. Həm demo_order cədvəlində sütun, həm proses dəyişəni, həm də BPMN business key kimi saxlanılır. Xarici sistem yalnız bunu bilir.

Kod

OrderService.java
public ProcessInstance createOrder(String customerName, BigDecimal amount) {
    String correlationId = UUID.randomUUID().toString();   // biznes açarı BİZ yaradırıq

    Map<String, Object> variables = new HashMap<>();
    variables.put("correlationId", correlationId);
    variables.put("customerName", customerName);
    variables.put("amount", amount);

    // 2-ci arqument = business key. Cockpit-də axtarış üçün, həm də
    // processInstanceBusinessKey() sorğuları üçün.
    return runtimeService.startProcessInstanceByKey(PROCESS_KEY, correlationId, variables);
}

public boolean notifyPaymentReceived(String correlationId) {
    try {
        runtimeService.createMessageCorrelation("PaymentReceived")
                .processInstanceVariableEquals("correlationId", correlationId)
                .correlateWithResult();
        return true;
    } catch (MismatchingMessageCorrelationException e) {
        // Ya belə instansiya yoxdur, ya da o, hazırda mesaj gözləmir.
        // Bu fərq Bənd 7-də həlledici olur.
        return false;
    }
}

Korrelyasiya metodlarının fərqi

MetodDavranış
correlate()Tam bir instansiya tapmalıdır. Tapmazsa və ya birdən çox taparsa istisna atır.
correlateWithResult()Eyni, amma nəticə obyekti qaytarır (hansı instansiya, hansı tip).
correlateAll()Uyğun gələn hamısını irəlilədir. Broadcast üçün.
correlateExclusively()Pessimistik kilid alır. Eyni instansiyaya paralel mesajlar gələndə optimistic locking istisnalarının qarşısını alır.
Testdə tapdığım incəlik Event-based gateway arxasında park olunmuş execution-lar ActivityInstance ağacında catch event-in deyil, gateway-in öz activity id-si ilə görünür. Yəni isWaitingAt("Event_PaymentReceived") yox, isWaitingAt("Gateway_WaitForEvent") yazmaq lazımdır. Bunu ağacı çap edərək tapdım — sənəddə açıq yazılmır.
OrderPaymentCorrelationTest.java — mahiyyət

        .correlateWithResult();

6. Bənd 2 — DMN qərar cədvəli

Niyə DMN, if-else deyil?

Risk hədləri biznes qaydasıdır. Onlar dəyişəndə (və dəyişəcəklər) kodun yenidən kompilyasiya olunması, review, deploy tələb olunmamalıdır. DMN cədvəli biznes analitikin oxuya və redaktə edə biləcəyi artefaktdır — və Camunda onu ayrıca versiyalaşdırır.

Cədvəl

< 100LOWBirbaşa ödəniş gözləməyə
[100..1000)MEDIUMBirbaşa ödəniş gözləməyə

Bu layihədə real dərs İlk versiyada DMN riskLevel hesablayırdı — və heç nə etmirdi. Dəyər hesablanıb dəyişəndə qalırdı, proses ona görə dəyişmirdi. Bu, "DMN əlavə etdim" deyib əslində heç nə göstərməyən demo idi. Exclusive gateway və manual review task əlavə etdikdən sonra DMN-in nəticəsi həqiqətən axını idarə etməyə başladı. Müsahibədə DMN-dən danışırsınızsa, mütləq göstərin ki, çıxış nəyisə dəyişir.

7. Bənd 3 — Saga və Compensation

Problem

Ödəniş qeydə alınıb (PAID), sonra çatdırılma provayderi sifarişi rədd edir. İndi sistemdə uyğunsuz vəziyyət var: müştəri ödəyib, amma heç nə göndərilməyəcək.

Bu, klassik distributed transaction problemidir. İki fərqli sistem (ödəniş + çatdırılma) arasında ACID tranzaksiya yoxdur. Saga pattern-i cavabdır: hər addımın kompensasiya edən əks addımı olur, və uğursuzluqda artıq icra olunmuş addımlar tərs sıra ilə geri alınır.

Kompensasiya ≠ rollback Database rollback commit olunmamış dəyişikliyi silir və heç bir iz qalmır. Kompensasiya isə artıq commit olunmuş və dünyaya görünmüş addımı əks əməliyyatla balanslaşdırır. Ona görə status AWAITING_PAYMENT-ə qayıtmır — REFUNDED olur. Fərq auditdə görünür və görünməlidir.

BPMN quruluşu — 4 element

order-payment-correlation.bpmn
<!-- 1. Kompensasiya olunan task-a bağlı boundary event -->
<bpmn:boundaryEvent id="Boundary_MarkPaidCompensation" attachedToRef="Task_MarkPaid">
  <bpmn:compensateEventDefinition/>
</bpmn:boundaryEvent>

<!-- 2. Handler. isForCompensation → normal axında HEÇ VAXT işləmir -->
<bpmn:serviceTask id="Task_RevertPayment" name="Revert Payment"
    isForCompensation="true"
    camunda:delegateExpression="${revertPaymentDelegate}"/>

<!-- 3. Tetikləyici: boundary error event → throw compensation -->
<bpmn:intermediateThrowEvent id="Event_ThrowCompensation">
  <bpmn:compensateEventDefinition/>
</bpmn:intermediateThrowEvent>

<!-- 4. Bağlantı. DİQQƏT: bu, <bpmn:process>-in SON uşağı olmalıdır -->
<bpmn:association sourceRef="Boundary_MarkPaidCompensation"
                   targetRef="Task_RevertPayment"/>
XSD tələsi — bir saatımı yedi BPMN sxemində tProcess tipi bütün flowElement-ləri artifact-lardan əvvəl tələb edir. <bpmn:association> artifact-dır. Onu sequence flow-ların arasına qoysanız deployment belə bir xəta ilə çökür:
stderr
cvc-complex-type.2.4.a: Invalid content was found starting with
element 'bpmn:serviceTask'. One of '{artifact}' is expected.
Həll: association-ı </bpmn:process>-dən dərhal əvvələ köçürmək.

Biznes xətası vs texniki xəta — bənd 3-ün əsl dərsi

NotifyShippingDelegate.java
@Override
public void execute(DelegateExecution execution) {
    String customerName = (String) execution.getVariable("customerName");
    if (customerName == null) return;

    if (customerName.contains("ShipFail")) {
        // BİZNES nəticəsi: provayder sifarişi rədd etdi. Bu, modelləşdirilmiş
        // haldır → boundary error event tutur → kompensasiya.
        throw new BpmnError(SHIPPING_FAILED_ERROR_CODE,
                "Shipping provider rejected the order for " + customerName);
    }

    if (customerName.contains("TechFail")) {
        // TEXNİKİ nasazlıq: şəbəkə qırılıb. Bu, modelləşdirilmiş hal DEYİL →
        // engine retry edir → retry-lar bitəndə incident.
        throw new IllegalStateException("Shipping provider unreachable for " + customerName);
    }
}
AtılanEngine nə edirSifarişin sonu
BpmnErrorBoundary error event tutur → kompensasiya işə düşürREFUNDED
RuntimeExceptionR3/PT10S üzrə retry, sonra incidentPAID qalır, proses park olunur
Niyə bu fərq kritikdir Rədd edilmiş çatdırılma modelləşdirilmiş biznes nəticəsidir — kompensasiya doğrudur. Qırılmış bağlantı isə deyil. Onu kompensasiya etmək o deməkdir ki, şəbəkə problemi ucbatından ödəmiş müştərinin pulunu səssizcə geri qaytarırsınız. Doğru davranış retry, sonra isə operatorun Cockpit-də müdaxiləsidir.

8. Bənd 4 — Engine daxili: async, retry, incident

asyncBefore nədir?

Job executor tənzimləməsi — real trade-off-lar

ParametrTrade-off
max-pool-sizeJob icra edən thread-lər. Az olsa throughput boğulur; çox olsa darboğaz DB connection pool-a keçir. Hikari pool ölçüsündən böyük olmamalıdır — əks halda thread-lər connection gözləyir.
queue-capacityAlınmış, amma hələ icra olunmamış job-lar. Böyük növbə backpressure-i gizlədir və çökmə zamanı itən işin pəncərəsini uzadır.
max-jobs-per-acquisitionBir dövrədə neçə job kilidlənir. Artırmaq DB gediş-gəlişini azaldır, amma klasterdə node-lar arasında optimistic locking rəqabətini artırır.
lock-time-in-millisƏn təhlükəli parametr. Ən yavaş real job-dan uzun olmalıdır. Qısa olsa, job hələ işləyərkən başqa node onu götürür və iki dəfə icra olunur.
Klaster davranışı — tez-tez soruşulur Camunda 7-də job executor-lar mərkəzi koordinator olmadan işləyir: hər node SELECT ... FOR UPDATE bənzəri sorğu ilə job-ları kilidləyir. Konfliktlər OptimisticLockingException kimi görünür və normaldır — engine həmin dövrəni sadəcə buraxır. Log-da bunları görmək nasazlıq əlaməti deyil; çox görmək isə max-jobs-per-acquisition-ın böyük olduğunu göstərir.

Worker kodu

InvoiceWorker.java
@Scheduled(fixedDelayString = "${demo.invoice-worker.poll-interval-ms:2000}")
public void pollForWork() {
    List<LockedExternalTask> tasks = externalTaskService
            .fetchAndLock(MAX_TASKS_PER_FETCH, WORKER_ID)
            .topic(TOPIC, LOCK_DURATION_MS)
            // Worker lazım olan dəyişənləri ADI ilə istəyir. Ona heç vaxt
            // baza bağlantısı verilmir — prosesə yeganə bağı bu payload-dır.
            .variables("correlationId")
            .execute();

    tasks.forEach(this::handle);
}

private void handle(LockedExternalTask task) {
    String correlationId = (String) task.getVariables().get("correlationId");
    try {
        String invoiceNumber = generateInvoice(correlationId);
        externalTaskService.complete(task.getId(), WORKER_ID,
                Map.of("invoiceNumber", invoiceNumber));
    } catch (RuntimeException e) {
        // Retry siyasəti BURADA yaşayır, modeldə deyil.
        Integer remaining = task.getRetries();
        int retriesLeft = remaining == null ? INITIAL_RETRIES : remaining - 1;

        externalTaskService.handleFailure(task.getId(), WORKER_ID,
                "Invoice generation failed", e.toString(), retriesLeft, RETRY_BACKOFF_MS);
    }
}
fetchAndLock — konkurentliyin bütün hekayəsi On eyni worker eyni topic-i poll edə bilər. Lock onların eyni işi iki dəfə görməsinin qarşısını alır. Test bunu birbaşa göstərir: worker-1 götürəndən sonra worker-2 boş siyahı alır; unlock()-dan sonra isə götürə bilir.
Nəqliyyat qatı haqqında dürüst qeyd Normalda worker /engine-rest-i HTTP üzərindən poll edir (camunda-external-task-client) — məhz bu, onu istənilən dildə ayrıca deployment edə bilməyə imkan verir. Bu stack-də mümkün olmadı: Camunda 7.24-ün REST starter-i Jersey üzərində qurulub, Spring Boot 4 isə Jersey dəstəyini tamamilə çıxarıb. Ona görə worker engine-side ExternalTaskService-i birbaşa çağırır. Əməliyyatlar eynidir — REST client məhz bunları wrap edir — yəni çatışmayan şəbəkə hop-udur, pattern deyil.

@KafkaListener(topics = "${demo.kafka.payment-events-topic}",
               groupId = "${demo.kafka.consumer-group}")
public void onPaymentEvent(String correlationId) {
    Optional<Order> order = orderService.findByCorrelationId(correlationId);

    if (order.isEmpty()) {
        // Gözləmək sifariş yaratmır → retry mənasızdır.
        throw new UnknownOrderException(correlationId);      // non-retryable → DLT
    }

    if (order.get().getStatus() != OrderStatus.AWAITING_PAYMENT) {
        // TƏKRAR çatdırılma. Status dedup açarıdır.
        return;                                              // no-op
    }

    if (!orderService.notifyPaymentReceived(correlationId)) {
        // Korrelyasiya xətası adətən "səhv" yox, "TEZ" deməkdir:
        // instansiya hələ mesaj event-inə çatmayıb (məsələn manual review-dadır).
        throw new NotWaitingForPaymentException(correlationId);  // retryable
    }
}

12. Bənd 8 — OAuth2 / OIDC

Resource server nədir?

/api/** resource server-dir: gələn bearer token-i Keycloak-ın dərc etdiyi imza açarları ilə yoxlayır və içindəki rollara görə icazə verir. Bu tətbiqə heç vaxt parol çatmır və hər sorğuda Keycloak-a gediş-gəliş olmur — imza və iss/exp claim-ləri kifayətdir.

Ən çox rast gəlinən səhv

Rollar scope-da deyil Spring Security-nin default JwtGrantedAuthoritiesConverter-i scope/scp claim-inə baxır. Keycloak isə realm rollarını realm_access.roles-a qoyur. Nəticədə tamamilə etibarlı token heç bir rol vermir və bütün hasRole yoxlamaları uğursuz olur — bu isə token problemi kimi görünür, halbuki mapping problemidir.
KeycloakRealmRoleConverter.java
public class KeycloakRealmRoleConverter
        implements Converter<Jwt, Collection<GrantedAuthority>> {

    @Override
    public Collection<GrantedAuthority> convert(Jwt jwt) {
        Map<String, Object> realmAccess = jwt.getClaimAsMap("realm_access");

        if (realmAccess == null
                || !(realmAccess.get("roles") instanceof Collection<?> roles)) {
            return List.of();   // rolsuz istifadəçi = 403, 500 deyil
        }

        return roles.stream()
                .map(String::valueOf)
                .map(role -> (GrantedAuthority) new SimpleGrantedAuthority("ROLE_" + role))
                .toList();
    }
}

Client rolları isə tamam başqa yerdədir: resource_access.<clientId>.roles.

isWaitingAt("Event_PaymentReceived") uğursuz oldu. ActivityInstance ağacını çap edəndə məlum oldu ki, gateway arxasında park olunmuş execution-lar gateway-in öz id-si (Gateway_WaitForEvent) ilə görünür — fərdi catch event-lərin id-si ilə deyil, ta ki budaqlardan biri həqiqətən işə düşənə qədər.

13.7 BPMN fayl "özbaşına" geri qayıtdı

Gateway və user task əlavə etdikdən sonra UI-də 6000 dəyəri review task yaratmadı. Araşdırma göstərdi ki, deploy olunmuş versiyada gateway yoxdur — sonra isə grep sübut etdi ki, faylın özü diskdə geri qayıdıb (yəqin IDE bağlananda köhnə buferi yazıb).

Nəticə Məhz bu hadisə git init-ə səbəb oldu. Versiya nəzarəti olmadan belə bir şeyi aşkarlamaq və bərpa etmək çox baha başa gəlir.

14. Müsahibə üçün sual-cavab

Camunda əsasları

SualQısa cavab
Embedded və standalone engine fərqi?Embedded — engine tətbiqin JVM-ində, tranzaksiya paylaşılır, delegate-lər sizin bean-lərinizdir. Standalone — ayrıca server, REST ilə müraciət, delegate-lər serverin classpath-ində olmalıdır (ya da external task).
Wait state nədir?Engine-in tranzaksiyanı commit edib dayandığı nöqtə: user task, mesaj/timer catch event, external task, async continuation.
Business key nə üçündür?Proses instansiyasını biznes obyektinə bağlamaq. Cockpit-də axtarış, processInstanceBusinessKey() sorğuları.
Message correlation necə işləyir?act_ru_event_subscr-də abunəliklər saxlanılır; korrelyasiya dəyişən/business key üzrə indeksli axtarışdır. correlate, correlateAll, correlateExclusively fərqləri.

Xəta idarəetməsi

SualQısa cavab
BpmnError nə vaxt, exception nə vaxt?BpmnError — modelləşdirilmiş biznes nəticəsi, boundary error event tutur. Exception — texniki nasazlıq, engine retry edir, sonra incident. Texniki xətanı kompensasiya etmək = şəbəkə problemi ucbatından müştəriyə pul qaytarmaq.
Incident nədir və nə vaxt yaranır?Job-un retry-ları 0-a çatanda act_ru_incident-ə sətir yazılır. Proses ölmür — park olunur. Operator Cockpit-də səbəbi düzəldib retry-ı sıfırlayır.
Saga pattern-i Camunda-da necə qurulur?Kompensasiya olunan task-a compensateEventDefinition-lı boundary event, isForCompensation="true" handler, aralarında <association>, və tetikləmək üçün intermediateThrowEvent.
Kompensasiya rollback-dan nə ilə fərqlənir?Rollback commit olunmamış dəyişikliyi silir, iz qalmır. Kompensasiya artıq commit olunmuş və görünmüş addımı əks əməliyyatla balanslaşdırır — auditdə iz qalır (PAID → REFUNDED, AWAITING_PAYMENT deyil).

Engine daxili

SualQısa cavab
asyncBefore nə üçündür?Tranzaksiya sərhədi. Engine burada commit edir və qalanını job-a köçürür. Sonrakı addım çökərsə əvvəlki commit itmir.
asyncBefore vs asyncAfter?Before — activity-dən əvvəl commit; activity-nin özü retry olunur. After — activity-dən sonra; activity təkrar icra olunmur, yalnız sonrakı keçid.
lock-time-in-millis niyə vacibdir?Ən yavaş job-dan qısa olsa, job hələ işləyərkən başqa node onu götürür və iki dəfə icra olunur.
Klasterdə OptimisticLockingException?Normaldır. Node-lar eyni job-u kilidləməyə çalışır; engine həmin dövrəni buraxır. Çox görünürsə max-jobs-per-acquisition böyükdür.
Job executor pool ölçüsü nəyə görə seçilir?Hikari connection pool-dan böyük olmamalıdır — əks halda darboğaz sadəcə thread-lərdən DB bağlantılarına köçür.

Versiyalaşma və deployment

SualQısa cavab
Yeni versiya deploy edəndə işləyən instansiyalara nə olur?Heç nə. Onlar başladıqları definition-a bağlı qalır. Yalnız yeni instansiyalar yeni versiyanı götürür.
Onları necə köçürürsünüz?createMigrationPlan(src, tgt).mapEqualActivities().build() + newMigration(plan).processInstanceIds(...).execute(). Toplu üçün .processInstanceQuery(...) və .executeAsync().
Activity id dəyişibsə?Plan qurulur, amma execute() MigratingProcessInstanceValidationException atır və instansiya toxunulmamış qalır. Açıq .mapActivities("Old","New") lazımdır.
Timer müddəti dəyişibsə?.updateEventTrigger() — abunəlik yeni tərifə uyğun yenidən qurulur.

Inteqrasiya

SualQısa cavab
Service task nə vaxt, external task nə vaxt?Delegate — sürətli, JVM-daxili, engine tranzaksiyasında. External — uzun sürən iş, başqa dil/komanda, ayrıca scale, engine-dən asılı olmayan deployment. External task həm də wait state-dir: worker sönülü ikən heç nə xəta vermir.
fetchAndLock niyə lazımdır?Çoxsaylı worker eyni topic-i poll edir; lock eyni işin iki dəfə görülməsinin qarşısını alır. Lock müddəti ən yavaş işdən uzun olmalıdır.
Retry-a kim qərar verir?Delegate-də model (failedJobRetryTimeCycle). External task-da worker — handleFailure(..., retriesLeft, backoff), yəni xətanın növünə görə fərqli qərar verə bilir.
Dual write problemi nədir?DB commit-i və broker-ə göndərmə iki ayrı sistemdir, aralarında tranzaksiya yoxdur. Çökmə ya olmayan hadisə yaradır, ya da olmuş hadisəni itirir. Sıranı dəyişmək həll etmir.
Outbox necə həll edir?Event sətri status dəyişikliyi ilə eyni tranzaksiyada, eyni bazaya yazılır → atomikdir. Ayrıca publisher commit-dən sonra Kafka-ya göndərir. Qalan risk: ack ilə publishedAt arasında çökmə → at-least-once → consumer idempotent olmalıdır.
Niyə key = correlationId?Bir sifarişin bütün event-ləri eyni partition-a düşür → sıra qorunur; consumer həm də bu açarla dedup edir.
DLT niyə lazımdır?Daimi uğursuz record sonsuz retry olunub öz partition-unu bloklayır — arxasındakı bütün düzgün mesajlar dayanır.

Təhlükəsizlik

SualQısa cavab
Keycloak rolları niyə işləmir?Spring default converter-i scope-a baxır, Keycloak rolları realm_access.roles-a qoyur. Custom Converter<Jwt, Collection<GrantedAuthority>> və ROLE_ prefiksi lazımdır.
issuer-uri vs jwk-set-uri?issuer-uri OIDC discovery edir və iss claim-ini yoxlayır — başqa realm-ın düzgün imzalanmış token-i rədd olunur. jwk-set-uri yalnız açarları göstərir.
401 və 403 fərqi?401 — kim olduğunuzu bilmirik (autentifikasiya). 403 — bilirik, icazəniz yoxdur (avtorizasiya).
CSRF-i nə vaxt söndürmək olar?Stateless bearer token API-də — session/cookie yoxdursa, minmək üçün heç nə yoxdur. Cookie-li session forması varsa söndürmək olmaz.
Camunda webapp-larına SSO necə edilir?ContainerBasedAuthenticationFilter + OIDC principal-ı Camunda identity service-inə map edən AuthenticationProvider; ya da community Keycloak identity plugin-i.
